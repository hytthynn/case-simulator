# ADR-006 · Старт этапа 1 при незакрытых Q-01…Q-03

- **Дата:** 2026-11-06 · **Статус:** принято
- **Связано:** [`00-ТЗ.md`](../00-ТЗ.md) §25–27, [`14-open-questions.md`](../14-open-questions.md), [`07-security.md`](../07-security.md), [`09-monetization.md`](../09-monetization.md)

## Контекст
`AGENTS.md` и ТЗ фиксировали: «stage 0 — код ещё не создан. Не начинать реализацию без Q-01…Q-03». Заказчик дал команду начать разработку. При этом:

- **Q-01** (`BOT_TOKEN`, `@username`, @BotFather, 2FA) и **Q-02** (домены, доступы Cloudflare/Railway/Supabase/GitHub) требуют внешних учётных данных, которые агент получить не может.
- **Q-03** (юридическое заключение по ассетам Valve, R-01) блокирует **релиз**, но не разработку.
- `14-open-questions.md` §5 и `00-ТЗ.md` §27 уже определяют механизм на этот случай: «закрыты Q-01…Q-14 **или явно зафиксированы принятые допущения**».

## Рассмотренные варианты
| Вариант | Вердикт |
|---|---|
| Остановить работу до ответов заказчика | ❌ теряется весь объём работ, не зависящий от доступов |
| Начать полный этап 1 с заглушками секретов в репо | ❌ нарушает правило №7 `AGENTS.md` и NFR-10/12 |
| **Начать credential-free часть этапа 1, зафиксировав допущения и границы** | ✅ принято |

## Решение
1. **D-07:** interim-допущения §5 `14-open-questions.md` объявляются действующими до ответов заказчика: официальные веса CS2, StatTrak 10 %, RTP 0.95–0.97, `xp(n)=round(1440·n^1.35)`, стартовый баланс $10, interim-прайс XTR, RU 100 %. Все такие значения помечены `INTERIM [Q-xx]` в коде и БД.
2. Разрабатывается только то, что **не требует секретов и внешних доступов**: монорепо, контракты, SQL-схема/RLS/RPC, серверный каркас, SPA-шелл, CI и документация.
3. Секреты (`BOT_TOKEN`, service key, приватный JWK, `DATABASE_URL`) **не появляются** в репозитории, логах и клиентском бандле. При их отсутствии сервис стартует в `dev`-режиме на in-memory БД; `/health` явно возвращает `production_ready: false`.
4. **Запрещено до закрытия Q-01/Q-02:** реальная авторизация через Telegram, установка webhook, выставление XTR-инвойсов, деплой в staging/prod. `deploy.yml` пропускает сетевые шаги без секретов.
5. **Q-03 остаётся блокером публикации:** ассеты 1:1 (D-03) не выгружаются в Storage до юридической проверки R-01; `verify-assets.mjs` по умолчанию работает в нестрогом режиме.
6. Provably-fair RNG реализован в SQL RPC через `pgcrypto` в фиксированной схеме `extensions` (совместимо с Supabase и локальным Postgres); никакого `Math.random()`.
7. На этапе 1 вместо `@telegram-apps/sdk` используется типизированный адаптер `window.Telegram.WebApp` с проверкой `isVersionAtLeast()` — см. **BUG-011**. SDK подключается при появлении реального TMA-окружения.

## Последствия
**Плюсы:** разработка идёт параллельно с получением доступов; весь код проверяем локально (`pnpm lint/typecheck/test`, `docs-lint`, pgTAP); ни одного секрета в git; границы ответственности зафиксированы.
**Минусы:** in-memory адаптер — не источник истины и не заменяет Supabase; часть экранов в браузерном превью работает в read-only demo-режиме; точная таблица дропа и ассеты появятся только на этапе 2.

## Проверка
- `GET /health` → `production_ready: false` без секретов.
- `pnpm docs:lint` проверяет отсутствие секретов/клиентской игровой логики.
- `ci.yml` поднимает локальный Supabase и прогоняет pgTAP (RLS + идемпотентность).
- Закрытие Q-01/Q-02/Q-03 оформляется новой записью D-08 + строками в `13-changelog.md`.

## Что закрыть перед этапом 2
Q-01, Q-02, Q-04, Q-05, Q-06, Q-07, Q-12; BUG-011.
